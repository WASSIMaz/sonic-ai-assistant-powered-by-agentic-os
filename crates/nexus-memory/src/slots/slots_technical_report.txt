## `event_log_buffer.rs` ✅ Aligned with one structural fix already applied

The uploaded version uses true ring semantics with monotonically incrementing `write_index` and a separate `drain_index`. This is correct and an improvement over the earlier skeleton that did not have `drain_index`.

**One real problem:** The wrap-around handling in `append()` has a logic error. When `phys_offset + event_size > capacity`, it writes to offset 0 instead of the correct wrap-around position. This silently drops the event that was mid-boundary and writes the new event at offset 0, potentially overwriting an existing record. For fixed-size `EventRecord` structs, the correct solution is to ensure events are always aligned so they never straddle the boundary — meaning `capacity` must be a multiple of `size_of::<EventRecord>()`. This must be enforced at construction time.

## `capability_map.rs` ⚠️ Size problem and misalignment

`64 + 64 + 1 + 4 + 891 = 1024` bytes. Let me check alignment: `resource_ids: [u32; 16]` is 64 bytes, `resource_count: u8` is 1 byte, `hot_reload_version: u32` is 4 bytes — but `u32` requires 4-byte alignment. After the `u8`, there are 3 implicit padding bytes before `hot_reload_version` in `#[repr(C)]`. The architecture says the MachineProfile is a *frozen Python dataclass* held via `ArcSwap<Py<PyAny>>` in `MachineProfileStore` — not a Rust struct. The uploaded file defines it as a plain Rust `struct` with `Vec<String>` fields. This is not aligned with the architecture.

## `embedding_cache.rs` ✅ Aligned

The implementation is correctly aligned — `DashMap<u128, CacheEntry>` with `LruCache` inside a `Mutex` for eviction ordering, `xxh3_128` keying, 1024 entry cap.

**One race condition:** The `get()` method locks the `LruCache` to promote the key, but reads from `DashMap` without holding that lock. A concurrent `insert()` could evict the key from `LruCache` and `DashMap` between the `DashMap::get()` returning a reference and the `LruCache::get()` promoting it. The result is a use-after-eviction — the caller holds a reference to a value that has been evicted from the cache. The `DashMap` reference keeps the memory alive (Arc semantics), so this is not a memory safety issue, but the LRU ordering becomes inconsistent. The `get()` and the LRU promotion must be done under the same lock or the promotion must happen before the DashMap lookup.
