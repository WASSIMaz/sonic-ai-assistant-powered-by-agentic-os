Q4 — MEMORY SIZES:
IMMUTABLE region: 64MB upper bound, derived as follows. MachineProfile at its largest carries embeddings for 500 installed applications at 512 dimensions float32, which is 500 × 512 × 4 = 1MB for the matrix alone, plus behavior profiles from PRIORS.md averaging 2KB per app giving another 1MB, plus frozen metadata. WorldModel at peak carries 200 running processes at ~500 bytes each, 50 open windows at ~200 bytes each, full session state and clipboard content — approximately 2-4MB for the full object graph. Both objects are frozen and pointer-swapped atomically, so the region must hold two generations simultaneously during the swap window, doubling the peak requirement. 16MB comfortably holds two generations of both objects. 64MB is the upper bound with 4x headroom for unexpectedly large environments — machines with thousands of installed applications or deeply nested window hierarchies. This headroom is cheap given that IMMUTABLE is read-only after seal and never causes write pressure.
APPEND_ONLY region: 2MB total. The observation ring is 150 slots × 320 bytes cache-padded = 48KB. The event_log_buffer is a write-buffered ring allocated at 1MB, sized to hold approximately 10,000 events at an average of 100 bytes per event before the 500ms flush cycle. Total region is 48KB plus 1MB plus alignment padding, rounded to 2MB.
MUTABLE region: 8MB, derived as follows. GoalState slots at 1024 bytes fixed size, maximum 256 concurrent sub-goals across all active goals, gives 256KB. Agent registry at 512 bytes per entry, maximum 64 concurrent agents, gives 32KB. Token debt ledger, surface assignments, and capability map together at approximately 1MB for a busy session. Total active data is under 2MB, and 8MB gives 4x headroom for goal explosion scenarios where a single complex task decomposes into hundreds of sub-goals.
COMPUTE region: 256MB upper bound. Capability matrix at 1000 apps × 512 dimensions × 4 bytes = 2MB. HNSW index for semantic search over strategy files at approximately 50MB for a mature installation with thousands of learned workflows. Embedding cache for the 200 most recently used intent embeddings at 512 dimensions × 4 bytes × 200 = 400KB. Total active use is under 60MB. 256MB provides headroom for large app corpora and expanded HNSW graphs as the system learns over months of use.

Q5 — Slab allocator fixed slot sizes and required slab classes
The architecture mandates #[repr(C)] typed structs with no heap fragmentation, which means each slab class must serve exactly one fixed-size type. The documents establish four structurally distinct slot types that cannot share a slab:
Slab A — GoalContract slots, fixed at 3072 bytes each (next power of two above the 2100-2800 byte range). The GoalContract is the dispatch payload containing all four enrichment blocks: ranked app manifest at 200 tokens, environmental briefing at 150 tokens, route description at 200 tokens, and pre-failure signatures at 150 tokens. At 700 tokens total and approximately 3-4 bytes per token average, each slot is 2100-2800 bytes of content plus a Mutex and metadata header. Fixing at 3072 bytes eliminates internal fragmentation variance and makes slot index arithmetic a clean right-shift. These slots are protected by a Mutex per slot, updated every 200ms by the EnvelopeMonitor's resource_status write. The size difference from all other slot types makes a shared slab impossible.
Slab B — GoalState and SubGoalNode slots, fixed at 1024 bytes each. Each GoalDependencyGraph entry maps sub-goal IDs to SubGoalNode structs with agent_type, depends_on array, status enum, result payload pointer, contract_ref, and critical_path_len. The upper range of the 512-1024 byte estimate is chosen as the fixed size to ensure no slot ever overflows, and 1024 bytes gives clean power-of-two arithmetic. These slots live in MUTABLE_REGION under goal_states behind a parking_lot::RwLock. The dag adjacency data plus status fields are structurally incompatible with GoalContract width and AtomicU64 width alike.
Slab C — ObservationSnapshot slots, fixed at 320 bytes each, cache-line padded. These live in the observation_ring inside APPEND_ONLY_REGION. The write concurrency protocol is completely different from slabs A and B: a single atomic fetch_add on the write index, no lock. Fixing at 320 bytes pads the 256-byte struct to a multiple of 64 bytes, preventing false sharing between adjacent slots when multiple CPU Worker Pool threads read the ring simultaneously to construct WorldModel snapshots. Any size mismatch with the other slabs would break the ring buffer's contiguous layout invariant.
Slab D — AtomicU64 counter slots, fixed at 8 bytes each. tokens_consumed, steps_completed, heartbeat_ts, wall_clock_start — all the AtomicU64 and AtomicI64 counters that the EnvelopeMonitor, LLMGateway, and L2 Watchdog read via bare atomic operations with no lock. Fixing at 8 bytes means the slab is a flat array of naturally aligned 64-bit atomics, directly readable with a single load instruction. Mixing these with any larger struct slab would waste 99.7% of every slot in the larger slab.
Why these four and no more: The architecture explicitly calls out that the IMMUTABLE_REGION (WorldModel, MachineProfile) uses mprotect(PROT_READ) and atomic pointer swap — these are not slab-allocated per-use slots, they are single pinned regions. The COMPUTE_REGION (capability_matrix, hnsw_index, embedding_cache) is owned exclusively by the CPU Worker Pool with coordination-by-message rather than lock, so it also falls outside the slab pattern.



Q6 — ObservationSnapshot struct design
The struct must satisfy three hard constraints derived from the architecture: it must be #[repr(C)] (fixed binary layout for zero-copy ring writes), it must hold everything the Oracle produces in one 200ms poll, and it must be small enough that 150 slots fit in a region that never causes cache thrashing.
The Oracle's documented outputs determine the fields directly. The WorldModel snapshot shows exactly what the Oracle feeds it — here is the ObservationSnapshot struct as it must be defined:
rust
#[repr(C)]
pub struct ObservationSnapshot {
    pub timestamp_ns:       u64,      // 8  bytes — monotonic wall clock
    pub active_window:      [u8; 64], // 64 bytes — window title, null-padded
    pub active_process:     [u8; 32], // 32 bytes — process name
    pub active_pid:         u32,      // 4  bytes
    pub total_cpu_pct:      f32,      // 4  bytes — system-wide CPU %
    pub memory_used_mb:     u32,      // 4  bytes
    pub memory_total_mb:    u32,      // 4  bytes
    pub disk_free_gb:       f32,      // 4  bytes — primary volume
    pub disk_pressure:      u8,       // 1  byte  — LOW/MED/HIGH enum
    pub network_reachable:  u8,       // 1  byte  — boolean
    pub network_latency_ms: u16,      // 2  bytes
    pub clipboard_type:     u8,       // 1  byte  — TEXT/IMAGE/EMPTY enum
    pub _pad:               [u8; 3],  // 3  bytes — 4-byte boundary alignment
    pub goal_ids_active:    [u32; 4], // 16 bytes — up to 4 concurrent goal IDs
    pub causal_goal_id:     u32,      // 4  bytes — which goal caused this obs
    pub causal_agent_id:    u32,      // 4  bytes — Chronicler attribution
    pub live_app_count:     u32,      // 4  bytes — current installed app count
    pub _struct_pad:        [u8; 32], // 32 bytes — pad content to 256 bytes
    pub _cache_pad:         [u8; 64], // 64 bytes — pad slot to 320 bytes,
                                      //            one full cache line of separation
                                      //            between adjacent ring slots
}
// Slot size: 320 bytes. Content: 256 bytes. Separation pad: 64 bytes.
// 150 slots × 320 bytes = 48,000 bytes (~47KB). Fits in L3 cache.
Every field maps to a direct syscall output — /proc/stat for CPU, /proc/meminfo for memory, statvfs for disk, getActiveWindow for active_window and active_pid, network interface query for reachability and latency, clipboard type from the Oracle's event subscription. There is no probabilistic content in an ObservationSnapshot. Every value is a verified fact from the OS at the moment of the 200ms poll.
causal_goal_id and causal_agent_id are required by the Chronicler attribution requirement in the architecture — the Chronicler must reconstruct causal traces without post-hoc inference, and these fields make attribution a direct lookup rather than a join.
live_app_count carries the current number of installed applications at the time of the snapshot. This is written atomically by the MachineProfile refresh cycle alongside the capability matrix update in COMPUTE_REGION, and read by any Contextualizer that calls np.frombuffer() to reshape the matrix. The reshape call requires the live count, not the maximum allocated count, to produce a correctly dimensioned (num_apps, 512) array.
Ring memory footprint: 150 slots × 256 bytes = 38,400 bytes (~37.5 KB). At cache-line padding to 320 bytes per slot it becomes 48,000 bytes (~47 KB). Either way this is comfortably within L3 cache on any modern CPU, which is the design intent: the ring must be readable by the CPU Worker Pool with zero memory-bus pressure, since WorldModel snapshot construction from the ring runs on every 200ms cycle.
Why 150 slots is the right number: At 200ms polling cadence, 150 slots covers exactly 30 seconds of history. The architecture states this explicitly. Thirty seconds is the right window because it is long enough for the FleetMonitor to detect a stall (which triggers at anomalous step counts relative to PRIORS.md distributions), long enough for the Chronicler to reconstruct a causal trace after a sub-goal completes, and short enough that the ring is never expected to survive across goal boundaries — episodic memory begins with the Chronicler's YYYY-MM-DD.md append, not the ring.
Question 7:



The optimal design for Python layout discovery in NEXUS is hardened codegen: Option B as the primary mechanism, with Option A as a startup integrity guard

A single nexus_layout.toml file is the source of truth. At every cargo build, build.rs reads it, computes its SHA-256, and emits two files simultaneously: layout.rs (Rust constants) and _layout.py (Python ctypes.Structure definitions). Both files contain the same hash baked in as a constant. At runtime, Rust writes that hash into a 64-byte header at offset zero of the mmap. Python reads the header on startup and hard-aborts if the hash does not match. On the hot path, Python uses ctypes.from_buffer() with the compile-time constants — one pointer cast, no function calls, no header reads, no parsing.

 Developer changes ObservationSnapshot, runs cargo build — build.rs recomputes the hash, the new hash is baked into layout.rs but the old _layout.py still carries the old hash. Rust writes the new hash into the mmap header at startup. Python reads it, asserts against its own SCHEMA_HASH, finds mismatch, aborts immediately with NexusLayoutError: schema hash mismatch — _layout.py is stale, run cargo build. No silent corruption. No wrong reads. No undefined behaviour. The system refuses to start in an inconsistent state.

Q8 — Definitive answer
The optimal design is a hybrid: #[repr(C)] for the fixed scalar fields that Rust needs to read directly, combined with an atomic-pointer-swapped frozen Python dataclass for the variable object graph that only Python reads.
The #[repr(C)] slot in the TypedBuffer IMMUTABLE_REGION contains only the scalar fields that Rust components read directly in their hot loops  without going through Python: timestamp_ns as AtomicU64, active_pid as AtomicU32, cpu_pct_bits as AtomicU32 storing the f32 bits, memory_used_mb as AtomicU32, disk_free_gb_bits as AtomicU32, network_reachable as AtomicU8. These are the fields the L2 Watchdog, EnvelopeMonitor, and L1 Health Watchdog read at high frequency. Every field is a fixed-size primitive with a clean #[repr(C)] mapping. No Python object graph, no serialization, no GIL required on the read path.
The full WorldModel Python frozen dataclass — running_processes, open_windows, clipboard content, session state, and all variable-length data — lives as a Py<WorldModelSnapshot> held inside an ArcSwap. The Oracle builds the new snapshot each cycle under the GIL, wraps it as Py<WorldModelSnapshot> via Python::with_gil, then calls world_model_store.store(Arc::new(new_snapshot)). ArcSwap::store is atomic and does not require the GIL. Every reader calls world_model_store.load() which returns an owned Guard<Arc<Py<WorldModelSnapshot>>> — the Arc strong count is incremented atomically inside load(), the GIL is not required, and the object cannot be freed while the Guard is alive regardless of what the Python GC does. When the Guard drops, the Arc strong count decreases. The old snapshot is freed exactly when the last Guard drops and the last Python reference goes out of scope — double-guarded by Arc and Python refcount simultaneously, with no window where either side can free the object while the other holds a reference.
The write sequence under the GIL is: construct new WorldModel dataclass, freeze it, call Python::with_gil to wrap it as Py<T>-a PyO3's owned reference type, release the GIL, call ArcSwap::store. The GIL is held only for Python object construction, never for the atomic swap. Rust readers never need the GIL.

Q9 — Optimal reclamation strategy: Arc<WorldModelSnapshot> (Rust) + Python GC refcount

ArcSwap<Py<WorldModelSnapshot>> is the correct and complete reclamation mechanism for this architecture. It is not two systems running in parallel — it is one unified ownership chain where Rust's reference counting and Python's object lifetime are structurally coupled through a single type.
The ownership chain works as follows. Py<WorldModelSnapshot> is PyO3's owned reference to the Python frozen dataclass. It holds one strong CPython reference — the object's refcount increments when Py<T> is created and decrements when Py<T> is dropped. Arc<Py<T>> wraps that Py<T> in Rust's reference counting, allowing multiple Rust components to hold simultaneous references to the same Python object without touching the CPython refcount directly — they share ownership of the container, not of the Python object itself. ArcSwap<Py<T>> sits on top and provides the atomic swap and load operations with no lock on the read path.
Reclamation is a single unbroken sequence. When the Oracle calls ArcSwap::store with a new snapshot, the old Arc's strong count decrements. If all readers have dropped their Guards the count reaches zero, Rust drops the Arc, which drops the Py<T>, which decrements the CPython refcount, which frees the Python object. If any reader still holds a Guard the old Arc survives until that Guard drops naturally. The Oracle does not wait, does not spin, and has no knowledge of how many readers exist. There is no separate Python GC path running independently and no moment where two systems must be reasoned about simultaneously.
The write sequence keeps the GIL window minimal. The Oracle constructs the new frozen WorldModel dataclass entirely in Python, calls Python::with_gil to produce Py<WorldModelSnapshot>, then releases the GIL before calling ArcSwap::store. The atomic swap happens entirely outside the GIL. Rust readers load the current snapshot via world_model_store.load() which returns a Guard<Arc<Py<T>>> with the Arc strong count incremented atomically inside the load call — there is no window between loading the pointer and incrementing the count where the object could be freed. Rust readers never acquire the GIL.
Epoch-based reclamation and hazard pointers are both rejected. The swap rate is one per 200ms. Neither mechanism offers any advantage at this frequency and both add implementation complexity with no performance return. A mutex is rejected because even uncontended mutex acquisition adds microseconds of overhead to every WorldModel read, which occurs on the critical path of every agent dispatch cycle.


Q10 — Optimal design: np.frombuffer() as the zero-copy bridge
The key insight that unlocks the entire design is that a C-contiguous numpy float32 array is already a raw contiguous block of 4-byte IEEE 754 floats — byte-for-byte identical to &[f32] in Rust. There is no translation required. The mmap COMPUTE_REGION is the shared backing store, and both numpy and Rust point their respective array/slice types at the same physical memory.
The write path runs at startup and every 5 minutes on the MachineProfile refresh cycle. The CPU Worker Pool enumerates installed applications via the Tool Factory scan, feeds each capability description through the resident embedding model producing a float32[512] vector per application, stacks them into a (num_apps, 512) C-contiguous matrix via np.vstack(), writes the raw bytes into COMPUTE_REGION via std::ptr::copy_nonoverlapping through a PyO3 call, then atomically writes the current num_apps count into the live_app_count field of the most recent ObservationSnapshot and into a dedicated AtomicU32 slot in MUTABLE_REGION. Both writes complete before COMPUTE_WRITE_DONE is published to the Bus. The memcpy for a 1000-app corpus at 512 dimensions is 2MB, completed in under 1ms and invisible against LLM inference latency
The read path is the performance-critical operation, called once per goal by the Contextualizer to rank applications by semantic relevance. The reader first loads live_app_count from the MUTABLE_REGION AtomicU32 slot with Acquire ordering. It then calls np.frombuffer(mmap_region[MATRIX_OFFSET : MATRIX_OFFSET + live_app_count × 512 × 4], dtype=np.float32).reshape(live_app_count, 512). This creates a numpy array view with no allocation and no copy — the array header's data pointer addresses the COMPUTE_REGION bytes directly. The matrix multiplication against the intent embedding vector runs via BLAS operating on that raw float32 pointer, GPU-accelerated where available via the Tool Factory acceleration scripts. The entire ranking operation runs in sub-millisecond time.
The read is protected against the write window by the Bus coordination protocol. When the CPU Worker Pool begins a matrix refresh it publishes COMPUTE_WRITE_BEGIN. Contextualizers that receive this event complete their current ranking operation and pause before the next load. COMPUTE_WRITE_DONE releases them. Because matrix refreshes occur at most once per 5 minutes and ranking operations complete in under 1ms, a Contextualizer will at most complete one additional ranking before observing COMPUTE_WRITE_BEGIN — the pause window is negligible.
The schema hash guard from Q7 covers the matrix layout too: MATRIX_OFFSET, MATRIX_EMBEDDING_DIM, and MATRIX_MAX_APPS are all constants generated from nexus_layout.toml. If the embedding dimension changes (a new model with different output size), the schema hash changes, Python's startup assertion fails with NexusLayoutError, and the system refuses to start rather than silently computing incorrect dot products against a misaligned matrix.

Q11 — The sentinel is a PyO3 Rust struct
The sentinel must be a #[pyclass] Rust struct with #[pymethods] overriding every dunder. A pure Python class has a fundamental flaw that disqualifies it: Python looks up special methods on the type, not the instance, using CPython's internal slot table (tp_as_number, tp_as_sequence, tp_as_mapping). A pure Python class can define __bool__ as an instance method but CPython's slot mechanism accesses it through type(obj).__bool__ — if the lookup chain has any gap, the dunder is not called. More critically, a pure Python class is monkey-patchable at runtime: an agent module could in principle replace NamespaceViolation.__bool__ with a no-op, bypassing detonation entirely.
#[pymethods] in PyO3 hooks directly into CPython's slot table — the same slots that Python's own built-in types use. There is no bypass path because the slots are set at type-registration time in C, not in Python's mutable __dict__. The sentinel also carries its violation context — slot_id, agent_id, lamport_ts, operation — as fields inside the Rust struct. When detonation fires, the NamespaceViolationUsed exception message contains the full context automatically, with no thread-local lookup required.
The ten dunders that must be overridden are: __getattr__, __getitem__, __bool__, __iter__, __len__, __eq__, __str__, __repr__, __contains__, and __call__. Every one calls the same detonate() method which writes the USE event to SQLite synchronously and then raises NamespaceViolationUsed.

Q12 — Two-tier log: event_log_buffer for ACCESS, synchronous SQLite for USE
The asymmetry between ACCESS and USE events is not a stylistic choice — it maps directly to an asymmetry in what each event means and what must survive a crash.
ACCESS events are frequent. Every out-of-scope slot access attempt, every prompt injection probe, every namespace boundary test generates one. Writing each synchronously to SQLite would add 1-5ms to every such attempt, blocking the hot path the entire NEXUS architecture is designed to keep unblocked. Instead, ACCESS events write via a single atomic append into the event_log_buffer in APPEND_ONLY_REGION — one fetch_add on the write index followed by a struct copy into the designated slot, approximately 10ns, non-blocking, no lock, no SQLite interaction. The Event Log Flush thread drains the buffer to the security_events table in nexus.db every 500ms in a single batched write under WAL mode. Up to 500ms of ACCESS events can be lost on a hard crash. This is acceptable because an ACCESS event without a corresponding USE event means the sentinel was returned to the agent but never dereferenced — no corruption occurred, no agent crashed, and the audit gap carries no forensic consequence.
USE events are categorically different. When an agent actually dereferences a bad slot the system is in an error state, the agent is about to be terminated, and the forensic record must survive unconditionally. The USE event is written synchronously to SQLite inside detonate() before the exception is raised. The cost is 1-5ms. The agent is already in a crash path — that cost is irrelevant. The USE event record is self-contained and complete: full Python traceback to the exact line that triggered detonation, slot_id and agent_id from the CapabilityToken, operation attempted, lamport_ts for happened-before ordering, and a reference to the originating ACCESS event keyed on lamport_ts. The USE record must be self-contained because the ACCESS event it references may have been lost in a crash window — forensic reconstruction cannot depend on a join that might not resolve.
If detonate() fires before sqlite_ready is confirmed — which should not occur given SQLite is first in the bootstrap sequence but must be handled explicitly — the USE event is written to a pre-SQLite emergency buffer in APPEND_ONLY_REGION with a flag marking it as requiring promotion. Promotion happens as the first operation after sqlite_ready is set, before the flush thread begins its normal 500ms cycle. No USE event is ever silently lost regardless of when in the boot sequence detonation occurs.
The security_events table schema carries event_type, slot_id, agent_id, lamport_ts, operation, traceback, and access_event_ref. event_type distinguishes ACCESS from USE. traceback is NULL for ACCESS events and carries the full string for USE events. WAL mode ensures every synchronous USE write is an atomic append that does not block concurrent readers. Querying all events for a given lamport_ts window reconstructs the complete violation timeline — which agent targeted which slot, whether the sentinel was used, and the exact code path that triggered detonation.


Q13 — CapabilityToken in thread-local storage, set by Kernel, invisible to agent
The agent_id parameter option is rejected immediately because it is forgeable. Any agent — including one under prompt injection — can pass an arbitrary agent_id to read_slot(), access slots belonging to a different agent, and generate an audit log that blames the other agent. This is not a theoretical concern in a system that explicitly models prompt injection as its primary threat.
Thread-local storage alone is not sufficient either. If the TLS slot is accessible from agent code (even through a PyO3 call), a compromised agent can write a forged CapabilityToken into its own TLS and expand its namespace. The solution is to keep the TLS slot in Rust code that is not exported through the PyO3 API surface. The CURRENT_TOKEN thread-local is a Rust thread_local! macro — it is not accessible from Python at all. The agent module, which executes in Python, has no path to read or write it.
The Kernel sets CURRENT_TOKEN exactly once per agent thread, at spawn time, using the CapabilityToken it issued at GoalResourceGroup creation. The token's namespace field is an Arc<FrozenSet<SlotId>> — immutable once constructed, shared across all reads from that agent thread without copying. Every read_slot() and write_slot() call performs a TLS lookup (one pointer dereference into thread-local memory, ~1ns), extracts the token, checks token.namespace.contains(&slot_id) (O(1) hash lookup), and either proceeds or returns a NamespaceViolation with the full token context baked in. The agent call site is simply read_slot(WORLD_MODEL_SLOT) — no parameter, no boilerplate, and no surface for forgery.

Q14 — All four region protocols: confirmed with corrections
IMMUTABLE — confirmed, with a mandatory sequence correction. The mprotect(PROT_READ) plus atomic pointer swap is correct. The critical addition is that the sequence order matters for safety. The correct order is: write to a staging area while it is writable, call mprotect(PROT_READ) on the staging area to seal it, then perform the atomic pointer swap to make it visible. If the swap precedes the mprotect, there is a window where readers can load the new pointer and simultaneously a second writer could modify the region. The hardware protection must be in place before the pointer is published. This is a TOCTOU window that is easy to miss and catastrophic if it occurs.
APPEND_ONLY — confirmed. Ring wrap is silent overwrite, by design, not a bug. The fetch_add(1, SeqCst) with index % 150 is the correct and complete write protocol. When the ring wraps, the oldest slot is silently overwritten — this is the intended behaviour because the ring is sensory memory, covering exactly 30 seconds of observation history. No consumer legitimately needs an observation older than 30 seconds: the CPU Worker Pool reads the ring in batches to build WorldModel snapshots which are themselves preserved in hot tier. The one guard that must be added is a SeqLock-style check: readers snapshot write_index before reading, then verify it has not advanced by ≥ 150 slots during the read. If it has, the ring lapped the reader and the read must be retried. Without this check, a slow reader can receive a partial observation from a slot that was partially overwritten mid-read.
MUTABLE — confirmed, with explicit timeout handling. parking_lot::RwLock per slot with try_write_for(500ms) is correct. The critical detail is that try_write_for returns Option<RwLockWriteGuard> — None on timeout, never a panic. Every write call site must handle the None case explicitly: publish LOCK_TIMEOUT to the Bus carrying the slot_id and holder_agent_id, then wait for the L1 Agent Health Watchdog to identify and recover the stalled holder before retrying. The Lamport clock update via AtomicTimestamp::advance_to on every write is confirmed and necessary — it enables happened-before ordering across any two mutations anywhere in the system for post-mortem reconstruction.
COMPUTE — enforced by both Rust and Bus coordination, each for different operations. Write exclusivity is enforced by Rust via the CapabilityToken: COMPUTE_WRITE is not in any agent's namespace frozenset. Only the CPU Worker Pool's token includes it. This makes it structurally impossible for any agent to write to the COMPUTE_REGION — not a runtime check but a namespace enforcement at the TypedBuffer access layer. Read coordination during the 5-minute refresh window is handled by Bus events: COMPUTE_WRITE_BEGIN causes Contextualizers to pause matrix reads; COMPUTE_WRITE_DONE releases them. This is coordination-by-message rather than coordination-by-lock, which is why there is no RwLock on COMPUTE — the write window is so infrequent (once per 5 minutes) that lock contention would never occur anyway, and Bus coordination gives readers a clean signal rather than a lock timeout.
Q15: 
Boot ordering fix — the primary solution
SQLite must initialize at the very start of bootstrap, before any component that could generate events. This is already the documented intent — SharedMemoryBus init with WAL mode enabled is line one. If something in the implementation creates nexus.db later than this, that is the bug to fix. Move it back to where it belongs.
The flush thread behavior — the safety net
Regardless of boot ordering, the flush thread must never assume SQLite is ready. It checks a sqlite_ready flag before every drain attempt. If the flag is not set, it skips that flush cycle silently — the ring keeps accumulating, nothing drops. This costs nothing and protects against the small initialization window, slow disk, or any future boot ordering drift.
SQLite initialization failure — the hard case
If SQLite fails to initialize entirely — WAL corruption, migration failure, disk error — the system has one and only option :
Hard stop: NEXUS refuses to boot. Clean, safe, predictable. Correct for a system where auditability is a security requirement.
SQLite slow initialization — the middle case
WAL recovery from a prior crash is acceptable delay. Set a hard timeout — 5 seconds is reasonable. Within that timeout, the flush thread keeps skipping cycles and the ring accumulates. If SQLite comes up within the timeout, everything drains normally and nothing is lost. If the timeout expires without SQLite being ready, treat it as total failure and apply whichever policy you chose above.
The readiness gate
Do not declare "NEXUS ready" until sqlite_ready is confirmed. This is a single assertion at the end of bootstrap. It ensures no goal is ever accepted into a system where the audit and operational infrastructure is not fully live.
Q16 — SLAB ALLOCATOR: STATIC PRE-ALLOCATION
Static pre-allocation. All slots allocated at startup, marked available or used, never freed at the OS level for the lifetime of the process.
The architecture establishes hard maximums for every slot type: 256 GoalContract slots, 512 GoalState slots, 150 ObservationSnapshot slots, 1024 AtomicU64 counter slots. These numbers are fixed in nexus_layout.toml and baked into the schema hash.

Q18 — EMBEDDING CACHE: XXHASH, BOUNDED LRU AT 1024 ENTRIES
Hash function: xxHash (xxh3_128)
Maximum cache size: 1024 entries. At 512 float32 dimensions per vector, each entry is 2KB of vector data plus the xxh3_128 key and metadata — approximately 2.1KB per entry. 1024 entries is approximately 2.1MB total, comfortably within the COMPUTE_REGION 256MB ceiling and small enough to stay resident in L3 cache on any modern CPU.
Eviction policy: LRU. The access pattern is exactly what LRU is designed for — the Contextualizer embeds the same intent descriptions repeatedly across related sub-goals within a session, the Security Kernel re-embeds the root intent on every provenance check, and the resident model's output for a given text is deterministic so a cache hit saves the full embedding inference cost.
The DashMap implementation is confirmed from the architecture documents. DashMap provides concurrent reads and atomic writes with no global lock.
